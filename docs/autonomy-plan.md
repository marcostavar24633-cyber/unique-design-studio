# Unique Design Studio — план автономности уровня 3

## Цель

Перейти к циклу «наблюдать → диагностировать → подготовить исправление → проверить → PR → безопасное слияние → публикация → проверка результата». Изменения кода попадают в `main` только через Pull Request. Автоматизация не получает права менять защиту репозитория, обходить CI или публиковать Gateway.

## Этапы внедрения

1. **Merge Engine (#147).** Автономное слияние не более одного PR за запуск, только из основного репозитория и от владельца. Требуются зелёный CI, локальные тесты/сборка, чистый анализ конфликтов и секретов, метка владельца для чувствительных файлов. Неизвестные факты блокируют слияние.
2. **Monitor + backup + controlled rollback (этот PR).** Проверка Pages, Worker и AI binding каждые 15 минут; один синтетический AI inference probe в сутки; сбои регистрируются в одном GitHub Issue. Еженедельный архив исходников с проверкой SHA-256 и сроком хранения 90 дней. Откат Worker доступен только через ручной workflow_dispatch в существующем deploy-worker.yml с конкретным version ID и явным подтверждением.
3. **Автоматический rollback.** Следующий этап: сначала сохранять ID последней версии Worker, прошедшей smoke test после публикации; автоматический откат разрешать только после нескольких независимых неуспешных проверок и только на сохранённую last-known-good версию. Никакого выбора «предыдущей версии» вслепую.
4. **AI repair agent.** Диагностика логов и создание исправляющего PR. Агент не пишет напрямую в main; любые изменения проходят тот же Merge Engine. PR, затрагивающие безопасность, авторизацию, Wrangler, workflow или зависимости, требуют ручной метки владельца.
5. **Проверка после публикации.** Worker после deploy проходит повторные проверки Pages, /health и Workers AI binding. При неуспехе workflow завершается ошибкой; автоматический runtime rollback включается только после отдельной реализации и тестирования last-known-good.

## Политика мониторинга

- Pages: HTTP 200 и HTML-документ.
- Worker: `/health` возвращает `ok: true` и точное имя сервиса.
- AI binding: `/api/diagnostics` подтверждает наличие Workers AI binding.
- AI inference: раз в сутки отправляется синтетический Design Review запрос без пользовательских данных. Проверяется JSON-контракт и отсутствие auto-apply. Это smoke test провайдера/модели, а не полная проверка генерации лендинга.
- При сбое монитор открывает или обновляет Issue; в отчёт не записываются токены, содержимое пользовательских запросов или секреты.

## Резервные копии

- Еженедельный архив исходников Git HEAD; Git metadata, локальные секреты и переменные окружения не включаются.
- SHA-256, проверка gzip и чтение списка файлов выполняются до загрузки.
- GitHub Actions artifact хранится 90 дней. Это резерв исходников, не бэкап Cloudflare bindings, Workers secrets, GitHub Secrets или данных пользователей.
- Восстановление проверяется отдельно перед использованием архива.

## Откат

Cloudflare Worker rollback немедленно переключает трафик на выбранную версию и не возвращает состояние внешних ресурсов. Поэтому этот этап добавляет контролируемый ручной откат по конкретному version ID. Автоматический откат будет включён только после реализации и тестирования механизма last-known-good, пост-деплой health gate и защиты от ложных срабатываний.

## Жёсткие ограничения

- **Universal AI Gateway — только по Service Binding и только с цепочкой «Workers AI → Groq».** Запрет на шлюз снят владельцем 19.11.2026: текстовые запросы идут через шлюз, который вызывает ту же модель Workers AI и при исчерпании квоты переключается на бесплатный Groq (его условия допускают production). Цепочку для студии задаёт `PROJECT_FALLBACK_CHAINS` в шлюзе; добавлять в неё Gemini, OpenRouter, NVIDIA или платные API нельзя без отдельного решения владельца.
- Прямой Cloudflare Workers AI binding остаётся обязательным: он нужен для изображений и служит запасным путём, если шлюз недоступен.
- Не логировать секреты, prompt/response пользователей, персональные данные или токены.
- Не выполнять автоматический откат по одиночному таймауту.
- Не вливать PR без зелёного CI и полного набора обязательных проверок.
- Не сливать внешние PR автоматически.
