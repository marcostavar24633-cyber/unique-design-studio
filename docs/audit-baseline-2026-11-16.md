## 3. Подтверждённые сильные стороны

1. Движок отделён от интерфейса и имеет публичный API.
2. Генерация выполняется в последовательности normalize → concept → render → audit → registry/export.
3. Проект поддерживает старый формат JSON и сохраняет неизвестные поля для обратной совместимости.
4. Есть тесты на детерминированность, уникальность, контраст, XSS-экранирование, доступность разметки и совместимость.
5. Самостоятельная HTML-страница не требует обязательного серверного хранилища.
6. CI запускает unit/integration tests, build и Playwright E2E на push и pull request.

## 4. Основные производственные пробелы

### P0 — надёжность коммерческого действия
- Форма не гарантирует доставку заявки: mailto зависит от почтового клиента пользователя; formAction требует реально существующий endpoint.
- Нужно различать «форма размечена», «endpoint настроен» и «отправка подтверждена тестом».
- CTA с пустым или неподходящим назначением не должен считаться полноценным коммерческим действием.

### P1 — полнота QA
- Статический аудит не проверяет реальную доставку форм.
- Нет подтверждённого единого security checklist и deployment smoke test.
- Статические performance-индикаторы не заменяют лабораторные/полевые измерения.
- В отчёте нужно разделить pass, warning, fail и not-tested.

### P1 — SEO публикационного пакета
- Подтвердить наличие и корректность canonical, robots.txt и sitemap.xml в экспортируемом/публикуемом проекте.
- Schema.org должен формироваться только из подтверждённых данных.
- Проверять абсолютные URL и корректность домена после публикации.

### P2 — управление проектами
- Нужны явные версии/снимки проекта, журнал изменений, восстановление и проверка экспорта.
- Локальное хранение остаётся режимом по умолчанию; серверная БД не является обязательной.

### P2 — визуальные материалы и motion
- Отделить факт наличия фотографии от её содержательной релевантности.
- Не выдавать промпт на изображение за сгенерированное изображение.
- Ввести управляемые профили motion с fallback для reduced-motion и слабых устройств.

## 5. Рекомендуемый следующий технический этап

Начать с P0: улучшить контракт форм и CTA, чтобы интерфейс и QA не создавали ложное впечатление, будто заявка будет доставлена автоматически.

Предлагаемая модель состояния формы:
- not-configured — endpoint не задан;
- mailto-fallback — используется почтовая ссылка/клиент, доставка не гарантируется;
- endpoint-configured — задан HTTPS endpoint, но реальная доставка ещё не подтверждена;
- verified — успешная отправка подтверждена отдельным тестом/интеграцией.

Не записывать реальные персональные данные в тесты и не отправлять тестовые заявки реальным получателям.
